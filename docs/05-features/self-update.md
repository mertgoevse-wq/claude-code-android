# Self-update

Getting a new version of the app, and getting a new version of Claude Code. Two different things, both of which rot.

## Two update channels

| Channel | What updates | Frequency |
|---|---|---|
| The app | The APK, the code, the resources | Monthly-ish, or when something is broken |
| Claude Code | The engine binary inside the app's runtime | Often, sometimes within days |

They are separate because they fail differently and because a broken engine update is a much more likely event than a broken app release.

## The app update

### Where updates come from

| Source | How | Trust |
|---|---|---|
| The GitHub releases of this repository | The release feed, polled | Checksum and signature from the release |
| A bundled build | For a person building from source | Their own build |
| The Play Store, if installed from there | The store's own mechanism | The store |

**The app never installs a build it did not verify.** A release is fetched, its checksum compared against the value published alongside it, and only then offered. A mismatch is discarded and reported, and nothing is installed.

### The flow

```
Checking…  →  1.2.0 verfügbar  →  Changelog ansehen  →  Herunterladen (Fortschritt)
                                                          →  Prüfen  →  Installieren
                                                          →  Neustart
```

| Step | Behaviour |
|---|---|
| Check | On launch, at most once a day, and on demand from Settings. A check is a small HTTPS request to the release feed. |
| Silent | Never. A check is not a download, and a download is not an install. |
| The offer | A row at the top of Settings, and a notification. Not a modal, and not a full screen. |
| The changelog | Shown before downloading, from the release's own notes. Not generated by the app. |
| Download | Resumable, with a progress notification, and a cancel |
| Verification | Checksum, then a probe of the new package's metadata |
| Install | Only after an explicit confirmation, stating what will restart |
| Restart | The app restarts. A run in progress is handled per `05-features/background-execution.md`: marked interrupted, work committed to `wip/`, resume offered. |
| Rollback | The previous version's APK is kept until the new one has launched successfully once. A crash within the first launch rolls back. This is a genuine feature, not a nicety. |

### What an update never does

| Never | Reason |
|---|---|
| Install without confirmation | A person on a phone is entitled to know before their app changes |
| Install while a run is active | It would interrupt the run. The app offers to wait, or to interrupt and resume afterwards. |
| Install a downgrade | Unless the user explicitly rolls back, which is offered only when a new version has crashed |
| Change settings | A migration changes a schema. It never silently changes a preference. If a setting's meaning changed, the Settings screen says so, per `04-screens/13-settings.md`. |
| Ask for a broader permission | A new permission is requested in context, with an explanation, and never bundled into an update notice. |
| Run on a metered connection without saying so | A 30 MB download on a phone's data plan needs a confirmation. The app checks `NetworkMonitor`. |

## The Claude Code update

This is the risky one, and the whole design of the runtime exists because of it.

### The daily check

| Property | Behaviour |
|---|---|
| When | Once a day, on first launch, and on demand from Settings |
| What | A HEAD request to Anthropic's release endpoint for the current version, compared against the installed one |
| Size | Nothing. A version check is a few hundred bytes. |
| Failure | Silent, with a dated record. A failed check is not an error the user needs to see. |
| Storage | The last check timestamp, per profile |

### The update itself

```
1.2.283  installiert   →   1.2.290 verfügbar

[ Was ist neu ]     Die Versionshinweise des Anbieters
[ Herunterladen ]   184 MB, dauert bei 5 MB/s etwa 40 Sekunden

↓ Laden …
↓ Prüfen (Prüfsumme)
↓ Probe (einmal starten, Version prüfen)
↓ Austauschen
✓ 1.2.290 läuft
```

### The probe, and why it exists

This is the most important part of the whole update design.

A new Claude Code release can break the glibc patch. If the app swaps the binary and it no longer starts, the app is dead — the runtime is the product. So:

1. The new binary is downloaded to a staging location and its checksum verified.
2. It is patched.
3. **It is launched once, in isolation**, with a trivial prompt, and the app waits for a version banner.
4. Only if that succeeds is the old binary swapped out.
5. If it fails, the old one is kept, the new one is discarded, and the user is told: "Version 1.2.290 startet auf diesem Gerät nicht. Es wurde bei 1.2.283 geblieben." with a link to the details and a way to report it.

The probe is the difference between an update mechanism and a gamble.

### Rollback

| Property | Behaviour |
|---|---|
| What is kept | The current binary and the previous one. Two copies, about 400 MB. The storage screen shows both. |
| When rollback happens | Automatically, on a failed probe, or on a launch failure within 24 h of an update |
| What is recorded | In the log: the version, the failure, and the rollback |
| What the user sees | A clear line in Settings: "Zurückgerollt von 1.2.290 auf 1.2.283 · Grund: Start fehlgeschlagen" |
| Manual rollback | Available in Settings, with a confirm. Somebody who wants the older version on purpose should not have to fake a crash. |
| Failed rollback | If the previous binary also fails, the app enters a recovery state with a clear instruction to reinstall the runtime, and offers the button. This is the worst case, and it has a screen. |

### The storage question

Two binaries plus a runtime is a lot of a phone.

| Setting | Behaviour |
|---|---|
| Keep one version | Default. The current binary only, plus the previous during the 24 h window |
| Keep two versions | The previous one indefinitely, for a person who has been burned by an update |
| Disk pressure | Below 1 GB free, the older binary is removed, and the setting says so |
| Never | The app deletes a project, a conversation, or anything else to make room for a binary. The binary is the app's; the project is the user's. |

## Staged rollout of the app's own updates

Not a percentage-based rollout — that needs a server. What exists instead:

| Mechanism | Detail |
|---|---|
| The release feed | Points at the newest release. A user can pin a version in Settings and stop receiving newer ones. |
| Channel | "Stabil" and "Beta". A beta release is a separate tag. A user on the beta channel gets prereleases and the app says so in About. |
| No forced updates | None. A build that works stays working. The only exception is a build with a security defect, and that is stated explicitly, with what the defect is, rather than as "please update". |

## Security

| Concern | Control |
|---|---|
| The download source | HTTPS to the repository's release endpoint. No third-party mirror. |
| Integrity | A published checksum, compared before anything is offered |
| Signature | Where a release is signed, the signature is verified. Where it is not, the app says so rather than implying a guarantee. |
| The engine binary | Anthropic's own published checksum list, per `06-runtime/native-profile.md` |
| Storage | The APK is verified after writing as well as before, because a partial write is a real failure mode on a phone |
| Permissions | An update never carries a new permission silently. The manifest difference between the installed and the new version is computed and shown: "Diese Version fragt zusätzlich nach {permission}." before installing. |
| Uninstall | Android's own. Nothing the app does affects it. |

## States

| State | Behaviour |
|---|---|
| Up to date | A line in About: "Aktuell · geprüft vor 3 Stunden" |
| Update available | A row at the top of Settings and a notification. Never a modal. |
| Downloading | A progress notification, resumable, cancellable |
| Verifying | A short indeterminate state. It is a few hundred milliseconds and it is shown anyway, because "verifying" is the part a user wants to see. |
| Probe failed | A clear message, the old version kept, the new one discarded, a report link |
| Rollback happened | A line in About and a log entry |
| Both versions broken | A recovery screen with a reinstall action. This is the app's worst-case screen, and it is designed as such. |
| Offline | The check fails silently. The offer appears when connectivity returns. |
| The release feed is unreachable | Silent, dated. Not an error. |
| A metered connection | A confirmation before a download larger than 1 MB |
| A run is active | The install is blocked with an explanation and two options: wait, or interrupt and resume afterwards |
| An update while a run's plan is mid-flight | Never installed. Same as above. |

## What the user is told, exactly

No marketing language, no urgency, no exclamation marks.

| Situation | Text |
|---|---|
| An app update is available | "Version 1.2.0 ist verfügbar." with the release date, the size, and a changelog link. |
| An engine update is available | "Claude Code 1.2.290 ist verfügbar. 184 MB." |
| A probe failed | "1.2.290 startet auf diesem Gerät nicht. Die App bleibt bei 1.2.283." with the technical detail behind a disclosure. |
| A rollback happened | "Zurückgerollt von 1.2.290 auf 1.2.283." |
| A download is waiting on a metered connection | "WLAN verwenden?" with the size, and the two options. |
| An update was blocked by a run | "Ein Lauf arbeitet gerade. Aktualisieren unterbricht ihn." with "Warten" and "Unterbrechen und aktualisieren". |

## Testing

| Test | Type |
|---|---|
| `AppUpdateCheck` | Integration — at most once a day, resumable, silent on failure |
| `AppUpdateChecksum` | E2E — a release with a bad checksum is discarded, nothing is offered, and the failure is reported |
| `AppUpdateNoSilentInstall` | UI — every path to the install button requires a confirmation |
| `AppUpdatePermissionDiff` | E2E — a release with a new permission shows the difference before installing |
| `AppUpdateMetered` | UI — a download above 1 MB on a metered network confirms first |
| `AppUpdateBlockedByRun` | E2E — an install during a run is refused with both options, and "interrupt" commits to `wip/` and offers a resume |
| `AppUpdateRollback` | E2E — a crash in the first 24 h after an update rolls back to the previous APK automatically |
| `AppUpdateChannel` | E2E — a beta-channel user sees prereleases, and About says the channel is beta |
| `EngineUpdateDailyCheck` | Integration — once a day, a few hundred bytes, silent on failure, timestamped |
| `EngineUpdateProbe` | E2E — a binary that cannot start is detected by the probe, the old one is kept, and the message names both versions |
| `EngineUpdateRollback` | E2E — a failed launch within 24 h rolls back, and the log records both the failure and the rollback |
| `EngineUpdateBothBroken` | UI — the recovery screen with the reinstall action |
| `EngineUpdateStorage` | E2E — under 1 GB free, the older binary is removed, and no project file is touched |
| `EngineUpdateNoProjectDeletion` | E2E — a disk-pressure cleanup never removes a project, a conversation, or a log entry |
| `UpdateWording` | UI — asserts the texts in the table above, and that no exclamation mark appears in any update string |
| `UpdateNoUrgency` | UI — asserts no copy contains urgency language, and no update is a modal |
