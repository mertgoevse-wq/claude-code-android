# Signing and keystores

Signing is where a build becomes a release, and a leaked signing key is unrecoverable in practice — a new key means a new app identity and every install is lost. This document is deliberately paranoid.

## The key hierarchy

| Key | Purpose | Where it lives | Rotation |
|---|---|---|---|
| **Root** | Signs the release and debug-upload certificates. Nothing else. | An offline hardware token, in a physical safe. Never on a machine with a network connection. | Never. |
| **Release** | Signs the shipped APK/AAB | A CI secret, injected at release time, never persisted to disk | Every 2 years, or on any suspicion |
| **Upload** | Signs the Play upload | CI secret | Every 2 years |
| **Debug** | Signs `debug`, `benchmark`, `nightly` | A committed keystore, deliberately, with a documented password | Never; it protects nothing |
| **Test** | Signs instrumented-test APKs | Generated per CI run, discarded | Every run |

Only the root key is precious. The others are recoverable because they are, in the end, secrets in a secret manager — and if the secret manager is gone, rotating is a known, practised operation with a written procedure.

## The debug keystore is committed

This looks wrong and is not:

```
debug.keystore    (committed)
password: "android"
alias: "androiddebugkey"
```

The debug key protects nothing. It is in the Android SDK, it is documented by Google, it is in every Android project on Earth, and committing it means a fresh clone builds and runs without a setup step. Anyone who could use it to sign a malicious `dev.ccandroid.debug` could equally use a key they generate themselves.

What must never be committed: the release key, the upload key, `keystore.properties`, and any `.jks` other than `debug.keystore`. The `.gitignore` in `09-testing/test-data-safety.md` covers this, and a CI check asserts that the only keystore file in the repository is `debug.keystore`.

## `keystore.properties`

Generated by the release pipeline, present only inside the release job's workspace, deleted at the end of the job:

```properties
storeFile=/run/secrets/release.jks
storePassword=${from secret store}
keyAlias=ccandroid-release
keyPassword=${from secret store}
```

The build reads it only if it exists (`convention-plugins.md`, `cc.android.application`). A developer building locally has no `keystore.properties`, gets an unsigned `release` output, and `./gradlew installRelease` explains why it did nothing rather than producing a broken APK.

## The release pipeline

Signing happens in a workflow that a human triggers, on a tag:

```
1.  git tag v0.4.0 && git push origin v0.4.0
2.  GitHub Actions: release.yml
      a. checkout at the tag
      b. verify the tag is signed and points at a commit on main
      c. verify the versionCode in build.gradle.kts matches the tag
      d. retrieve the signing certificate from the secret store
      e. write keystore.properties into the workspace
      f. ./gradlew clean test check :app:assembleRelease :app:bundleRelease
      g. verify the APK signature with apksigner verify --print-certs
      h. upload the mapping file and the native symbols to the symbol store
      i. publish to the Play internal track
      j. delete keystore.properties and zero the keystore file
```

Steps (g) through (j) are the point. An APK that was signed with a key the pipeline did not expect is caught before it reaches a track. A mapping file that was not uploaded means the next crash report is unreadable, so it is uploaded before publication, not after.

## The fingerprint allowlist

The pipeline verifies the signing certificate fingerprint against a value committed in the repository:

```properties
# gradle/signing-fingerprints.properties
release=SHA256:7A:1C:...  (the real value, committed)
upload=SHA256:3E:9B:...
```

If the fingerprint that signed the artifact is not on the list, the build fails. This catches the case where someone replaces the keystore — the pipeline would happily sign with whatever secret it retrieved, and this is what makes that visible.

The fingerprints are public information, so committing them leaks nothing. They are in the Play console too; that is the point of a fingerprint.

## Play App Signing

We upload with the **upload** key and let Google re-sign with the **app signing** key. Consequence: the app signing key never leaves Google's infrastructure, which is one fewer secret to protect. Consequence: if upload-key access is lost, we can ask Google to reset it; if app-signing-key access is lost, the app is gone. The root key does not protect the app signing key, and this document does not pretend otherwise.

## ProGuard mapping and crash symbols

| Artifact | Uploaded where | When |
|---|---|---|
| `mapping.txt` (R8) | The crash backend, keyed by version | Every release, before publication |
| `native-debug-symbols` | The same | Every release |
| `DebugProbesKt.bin` | Discarded | Never shipped |
| Line numbers | `keepattributes SourceFile,LineNumberTable` | Enabled for `nightly` and `release` |

`SourceFile` and `LineNumberTable` slightly increase the APK size and are worth it: without them, a release stack trace is a list of obfuscated names and nobody can act on it.

## Certificate pinning for the runtime download

The Claude Code binary download is verified twice, and both verifications are recorded:

1. **Pinned digest.** The expected SHA-256 is a build-time constant from the runtime manifest, not a value fetched at download time. A compromised mirror cannot substitute a different binary.
2. **Signature, where available.** When the upstream release is signed, the signature is verified against a key that ships in the app. Where it is not, digest-only applies and the user is told so, once, in the diagnostics screen.

The download only begins after the digest is known. A download that cannot be verified is not started — see `06-runtime/native-profile.md`.

## Verification commands

```bash
# What key signed this artifact?
apksigner verify --print-certs app-release.apk

# Does it match what the pipeline expects?
apksigner verify --print-certs app-release.apk \
  | grep -F "$(grep release= gradle/signing-fingerprints.properties | cut -d= -f2)"

# Is the debug APK signed with the committed debug key? (CI asserts this)
apksigner verify --print-certs app-debug.apk | grep -F "androiddebugkey"

# Is the bundle signed with the upload key?
jarsigner -verify -verbose:summary app-release.aab | head
```

The last two run in CI on every push. A debug APK signed with something other than the debug key means the build configuration changed unexpectedly, and that is a failure, not a curiosity.

## Key rotation

When a key rotates:

1. A new key is generated **and signed by the root key**, producing a certificate.
2. The old key is kept until the platform confirms the new one works.
3. The fingerprint allowlist gains the new fingerprint; the old entry stays for one release cycle, marked.
4. The rotation is recorded in `15-appendix/changelog.md` with a date and a reason.
5. Six months later, the old key is destroyed.

The root-signed certificate chain is what lets a user (or a store) verify that a new key really is ours. Without the root key, rotation is a leap of faith — which is the whole reason the root key exists and the whole reason it lives in a safe.

## What a maintainer must do

If you are the maintainer and you are reading this for the first time:

- The root key's location and the safe's combination are recorded in a physical document, in a safe deposit box, and nowhere else digital.
- The release and upload keys are in the repository's secret store. Access is restricted to two accounts.
- If you lose the root key, nothing is immediately broken — the release key still works — but you can never rotate again, and the app is on borrowed time.
- Test the rotation procedure on a scratch package before you need it for real.
