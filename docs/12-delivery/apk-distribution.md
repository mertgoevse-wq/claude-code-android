# APK distribution

Three channels, one artefact pipeline. The signed APK is built once; the channels differ only in metadata and, for Play, in the artefact format.

## 1. What we ship

| Artefact | Built by | Signed with | Used by |
|---|---|---|---|
| `app-debug.apk` | `assembleDebug` | the debug key | Daily development, manual install, bug reports |
| `app-<version>-release.apk` | `assembleRelease` | the release keystore | Direct install, F-Droid-style manual distribution, the self-build flow |
| `app-release.aab` | `bundleRelease` | the release keystore | Play Store upload |

A universal APK is produced for the direct channel (`universalApk = true` in `10-build/build-variants.md`) because a hand-installed APK must run on any device, and because the self-build flow installs a file the app downloaded itself.

## 2. The pipeline

```
./gradlew clean check                 # all gates; a red gate stops here
./gradlew bundleRelease assembleRelease
fastlane android build --configuration release
scripts/verify_release.sh app/build/outputs/apk/release/app-release.apk
```

`verify_release.sh` checks, in this order and fails on the first failure:

1. The certificate fingerprint is in the committed allowlist.
2. The APK's `versionCode`/`versionName` match `version.txt` and are strictly greater than the last release.
3. The manifest has no debuggable flag, no test runner instrumentation hook, and no backup of secrets.
4. `check-no-analytics.sh` finds no tracking symbol.
5. `check-no-secrets.sh` finds no secret pattern in the resource table or assets.
6. `aapt2` reports the expected package id, `minSdk`, and `targetSdk` for this variant.

A failure at any step produces a non-zero exit and a message naming the check. There is no `--force`.

## 3. Versioning

`version.txt` at the repository root is the single source:

```
VERSION_NAME=0.4.0
VERSION_CODE=4
```

| Field | Rule |
|---|---|
| `versionName` | `MAJOR.MINOR.PATCH`, no suffix in a release build. Pre-release builds append `-N` |
| `versionCode` | Monotonically increasing integer, never reused, never reset. Incremented by one per release |
| Bumping | A spec amendment or a release checklist tick bumps it. A commit never bumps it silently |

Both are injected into the build through `buildConfigField` and into the About screen, so the About screen cannot disagree with the artefact.

## 4. Channel specifics

### Direct APK

- One file, one download page, one command for the user.
- The `NOTICE` about unofficial status and the licence must be shown before the download link, not in the footer.
- The SHA-256 of every release artefact is published next to the file. The self-update flow verifies it before installing.
- No CDN with tracking parameters. The file is served from the release assets or a static host the maintainers control.

### F-Droid

See `f-droid.md`. The constraint that shapes the build: **every dependency must be buildable from source with FOSS-only tooling.** If that is not possible, the reason is documented there and the recipe declares a prebuilt binary with its checksum.

### Play Store

See `play-store.md`. The constraint that shapes the build: Play requires an AAB, a data-safety form, a privacy policy URL, and a target-SDK that moves with the calendar.

## 5. The self-build flow

The app can rebuild itself. That is D28, and it is deliberately the *narrowest* possible version of itself:

| Step | Rule |
|---|---|
| Trigger | User taps "Check for update" in Settings → About. Auto-install is a separate, off-by-default switch |
| Source | A release feed the user can point anywhere, defaulting to the project's own release list |
| Verification | Signature fingerprint must be in the allowlist **and** SHA-256 must match the published value. Either mismatch stops the flow and says so |
| Install | `PackageInstaller` with the same signature requirement; the OS shows its own install confirmation, which the app does not attempt to bypass |
| Rollback | Before updating the bundled runtime binary, the previous version is kept. If the new binary fails `claude --version` twice, the app restores the previous one and files a field-error entry |
| What it may not do | Install an APK signed by another key, disable Play Protect, request device-owner privileges, or run `adb` |

If the update comes from a different signature than the installed app, the OS refuses it. That refusal is the security property; we do not work around it.

## 6. What is not distributed

- Debug symbols are uploaded to the crash reporter's local store, never published.
- The release keystore is never in the repository, never in a release asset, never in CI logs. See `10-build/signing-and-keystores.md`.
- Test fixtures containing realistic-looking keys are in the repository but are generated by `tools/`, carry a `.invalid` TLD, and are documented in `09-testing/test-data-safety.md`.

## 7. Failure modes

| Failure | What the user sees |
|---|---|
| Fingerprint mismatch on the downloaded APK | "This update is not signed by the same key as the installed app. Not installing." and the run continues on the existing version |
| SHA-256 mismatch | "The downloaded file is damaged or was altered. Not installing." with the expected and actual hash |
| Not enough storage | The exact free space required, and a link to the storage screen |
| Install declined by the user | Nothing. The app does not re-prompt on the next launch |
| Update installs but the runtime binary breaks | Automatic rollback, a field-error entry, and a notification that names both versions |
